# Local test credentials — how to get them, where to keep them

This replaces the ad hoc note that used to live at `lib/core/config/test`
(removed from the repo and its history in Phase 4 — see
`docs/phase7-preflight-report-2026-09-22.md` for that cleanup). **No real
device secret, staff PIN, or database credential belongs anywhere under
version control**, including as a "just for local testing" file — that file is
exactly how the previous one ended up committed.

## Getting a test device + staff PIN

These are generated by the backend's own operator tooling (`buskit-web`), not
hand-picked, and each is shown to you exactly once:

```
# First device for a company (creates its store + register + device + staff PIN in one go):
node database/pos_bootstrap_company.js \
  --company-id <id> --store-code <code> --store-name "<name>" \
  --register-code <code> --register-name "<name>" \
  --device-identifier <your-choice, e.g. DEV-TAB-1> \
  --salesman-id <your-choice, e.g. DEVSTAFF1> --pin <a PIN you choose>
```

The device secret is printed once, at the end of that command, and cannot be
retrieved again afterward (only its bcrypt hash is stored). Capture it
immediately into your local, gitignored notes.

For an additional device on an existing store, sign in with a device that
already has a staff token and call `POST /api/v1/pos/devices` (see
`Routes/posRoutes.js`) — its response also shows the new secret exactly once.

## Where to keep it locally

Put the identifier/secret/PIN in a file matching `*.local` (e.g.
`lib/core/config/dev.local` or `notes.local` at the repo root) or under a
`local/` folder — both are covered by `.gitignore`. Never place it as a plain
file directly under `lib/`, `test/`, or any other tracked path, even
temporarily; a file only becomes "temporary" once it's actually outside git's
reach.

## If a device secret or PIN is ever exposed (committed, screenshotted, sent in
chat, etc.)

Treat it as compromised immediately:
1. Deactivate the device: `PATCH /api/v1/pos/devices/:id/status` with
   `{"status": "inactive"}` (or your API's equivalent revoked state), using
   the device's numeric `id` (from `GET /stores/:storeId/devices`).
2. Create a replacement device (new identifier, fresh secret) the same way as
   above.
3. Rotate the staff PIN by re-running `pos_seed_staff_pin.js` for that
   `salesman_id` with a new PIN — it upserts, so this changes the existing
   PIN rather than creating a duplicate.

None of this should be run against a shared/production database without the
person who owns that database doing it or explicitly approving it.
